InterleaveGuard is a Go tool meant to find concurrency bugs like data races in programs. It goes through a few stages but they kind of overlap in practice. The first part parses the code with the usual Go parser and does type checking to map everything out. That gives it the AST info and package variables.

From there it builds a call graph by looking at direct calls inside the file. It also spots goroutine starts, both named ones and the anonymous kind, and it makes up some fake function names for those. Then it figures out what functions can reach from those starting points using a search over the graph. The next bit pulls out events from the function bodies. It marks reads and writes on shared variables and notices lock calls or channel stuff. It tries to match locks with unlocks to mark critical sections, including when unlocks are deferred. After that it checks for conflicts between functions that might run at the same time, but only if a write is involved and the accesses are not protected by the same locks.

I think the encoding part uses positions from the token package to keep order straight. Events get labels like READ or MUTEX_Lock and resources are just string versions of the expressions. The main data structure holds the functions, their events, the goroutine info and the dependencies found. It seems important that events stay sorted by source order and that critical sections pair up correctly. Shared conflicts only get checked on functions that can actually overlap in execution. Some of the reachability stuff might be simplified in how they describe it but the overall flow is parsing then graph stuff then the conflict detection.
