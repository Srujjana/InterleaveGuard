InterleaveGuard Engine Overview

## Architecture and Pipeline Stages
InterleaveGuard is a Go static analysis engine designed to detect concurrency issues, data races, and synchronization anomalies in concurrent Go programs. The pipeline operates through the following sequential stages:

1. **Parsing & Type Checking (Phase 1 / Entry Point):**
   - Parses Go source code using `go/parser` and `go/token`.
   - Performs static type-checking and name resolution using `go/types` and `go/importer` to establish precise AST-to-object mappings (`types.Info`, `Defs`, `Uses`, `Selections`).
   - Collects package-level variables and function declarations.

2. **Call Graph & Goroutine Extraction (Phase 2):**
   - Extracts direct call edges between functions declared within the analyzed file (`extractCallGraph`).
   - Identifies named and anonymous goroutine launches (`go func(...)`, `go target()`), constructing `GoroutineLaunch` records and synthetic function literals (`$goroutineN`).
   - Computes transitive reachability from goroutine entry points (`reachableFunctions`) using depth-first search (DFS) over the adjacency-list representation of the call graph.

3. **Event Extraction & Critical Section Modeling (Phase 2):**
   - Scans function bodies and anonymous function literals for concurrency-relevant operations (`extractEvents` / `extractEventsFromBody`).
   - Classifies shared-state operations on package-level variables into `READ`, `WRITE`, and `READ_WRITE` (assignments and increment/decrement statements).
   - Identifies synchronization method calls (`sync.Mutex`, `sync.RWMutex`, `sync.WaitGroup`) and channel operations (`CHANNEL_SEND`, `CHANNEL_RECEIVE`, `CHANNEL_CLOSE`, `SELECT`).
   - Lexically matches lock/unlock operations (`sync.Mutex.Lock`, `sync.RWMutex.RLock`, etc.) and deferred unlocks to construct `CriticalSection` intervals (`extractCriticalSections`).
   - Annotates shared-state events with enclosing lock protection (`annotateProtectedAccesses`).

4. **Dependency & Race Analysis (Phase 2):**
   - Establishes program-order dependencies (`PROGRAM_ORDER`) within functions.
   - Builds concurrent function pairs (`buildConcurrentFunctionPairs`) based on goroutine launch relationships and call graph reachability.
   - Detects shared resource conflicts (`SHARED_RESOURCE_CONFLICT`) between potentially concurrent functions where at least one operation is a write (`WRITE` or `READ_WRITE`) and accesses are not mutually excluded by matching locks (`ProtectedBy`).

## Encoding Conventions
- **Identifiers & Tokens:** AST positions (`token.Pos`) are used to establish precise source order and nesting relationships.
- **Event Kinds:** Strings representing concurrency primitives and memory accesses (`READ`, `WRITE`, `READ_WRITE`, `MUTEX_Lock`, `MUTEX_Unlock`, `RW_MUTEX_RLock`, `RW_MUTEX_RUnlock`, `CHANNEL_SEND`, `CHANNEL_RECEIVE`, `CHANNEL_CLOSE`, `WAITGROUP_Add`, `WAITGROUP_Done`, `WAITGROUP_Wait`, `SELECT`).
- **Dependency Kinds:** Classified as `PROGRAM_ORDER` or `SHARED_RESOURCE_CONFLICT`.
- **Resource Representation:** Stringified expressions (`resourceName`), supporting identifiers, selector expressions, pointer dereferences, and array index expressions.

## Key Precomputed Data Structures and Invariants
- **`ProgramModel`:** Aggregate container holding the target file path, parsed functions (`FunctionModel`), computed dependencies, goroutine launches, call graph edges, and goroutine executions.
- **`FunctionModel`:** Encapsulates function name, sequential list of ordered `Event` records, and sorted `CriticalSection` intervals.
- **`CriticalSection`:** Bounded by `startPos` and `endPos` (or block closing brace for deferred unlocks), tracking the lock resource and protected shared resources.
- **Invariants:**
  - Events within a function must be sorted in strict source-code order (`token.Pos`).
  - Critical sections must be correctly paired with corresponding unlocks (including handling of deferred unlocks in LIFO order).
  - Shared resource conflicts are only evaluated between functions that may execute concurrently.
